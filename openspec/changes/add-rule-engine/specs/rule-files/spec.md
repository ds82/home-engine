# Spec Delta

## Purpose

Defines how users author rules: the rule file format, how the engine discovers and loads TypeScript/JavaScript rule files, how rules are registered and identified, and how authors get typings and third-party dependencies.

## ADDED Requirements

### Requirement: Rule directory discovery
The engine SHALL recursively scan the configured rules directory for files ending in `.ts`, `.mts`, `.js` or `.mjs` and treat each match as a rule file. It SHALL exclude `node_modules`, any file or directory whose name starts with `_` or `.`, `*.d.ts` files and `*.test.*` / `*.spec.*` files.

#### Scenario: Nested rule files are found
- **WHEN** the rules directory contains `lights/hallway.ts` and `climate.js`
- **THEN** both files are loaded as rule files

#### Scenario: Helper modules are not loaded as rules
- **WHEN** the rules directory contains `_lib/helpers.ts` and `hallway.ts` imports it
- **THEN** `_lib/helpers.ts` is not loaded as a rule file, but `hallway.ts` can import it

#### Scenario: Excluded files are ignored
- **WHEN** the rules directory contains `types.d.ts`, `hallway.test.ts` and `node_modules/foo/index.js`
- **THEN** none of these files are loaded as rule files

### Requirement: TypeScript without a build step
The engine SHALL execute TypeScript rule files directly without requiring the user to compile them, including imports between local TypeScript files. It SHALL NOT type-check at load time; type errors are the editor's/CI's concern.

#### Scenario: TypeScript rule runs as-is
- **WHEN** the user places a `.ts` file using type annotations, interfaces and enums in the rules directory
- **THEN** the engine loads and runs it without any prior compilation by the user

#### Scenario: Syntax error reported
- **WHEN** a rule file contains a syntax error
- **THEN** the engine logs the file path, line and column of the error, does not load that file, and continues loading other files

### Requirement: Rules are registered by calling `rule()` or `setup()`
Rules SHALL be registered by calling the SDK function `rule()` (triggered rule) or `setup()` (setup rule) while the rule file is being evaluated. A file can register any number of rules, including rules created in loops or by user-defined factory functions with names computed at runtime. Exports of a rule file SHALL have no meaning to the engine.

#### Scenario: Multiple rules in one file
- **WHEN** `lights.ts` calls `rule("hallway motion", …)` and `rule("porch at sunset", …)` at top level
- **THEN** two rules are registered, `lights#hallway motion` and `lights#porch at sunset`

#### Scenario: Rules generated by a factory
- **WHEN** `presence.ts` defines `function notifyOnArrival(person, entity) { rule(`presence-${person}`, …) }` and calls it for `dennis` and `lydia`
- **THEN** two rules are registered, `presence#presence-dennis` and `presence#presence-lydia`

#### Scenario: Registration outside file evaluation
- **WHEN** rule code calls `rule()` or `setup()` later, for example inside a trigger callback
- **THEN** the call throws an error stating that rules can only be registered while their file is loaded, and no rule is registered

### Requirement: Triggered rule form
`rule(name, triggers, body, options?)` SHALL register a rule that runs `body` whenever any trigger in the `triggers` list fires (logical OR). `triggers` is a single trigger or an array of triggers (see rule-triggers and rule-scheduler). `options` MAY set `description`, `enabled` (default `true`), `id` (see Rule identity) and the concurrency `mode`.

#### Scenario: Several triggers, one body
- **WHEN** a rule is registered with `[onChange("binary_sensor.window_tilt"), onChange("binary_sensor.window_open")]` and the second sensor changes
- **THEN** the body runs once with an event describing the change of `binary_sensor.window_open`

#### Scenario: Rule disabled via options
- **WHEN** a rule is registered with option `enabled: false`
- **THEN** the engine registers it as disabled, never arms its triggers, and lists it as disabled in health output

### Requirement: Setup rule form
`setup(name, fn, options?)` SHALL register a setup rule: a rule whose function `fn` is called once each time the rule starts, without arguments. The function registers listeners (with `listen()`) and timers imperatively and may keep local state in closures. It MAY return a teardown function. `options` MAY set `description`, `enabled` and `id`, but SHALL NOT accept a concurrency `mode`. A setup rule is a rule in every other respect: it has a rule ID and status, and it is subject to storage, enable/disable and cleanup like a triggered rule.

#### Scenario: Stateful rule with local state
- **WHEN** a setup rule keeps a counter in a local variable and increments it in a listener it registered with `listen()`
- **THEN** the counter persists across listener invocations until the rule is unloaded

#### Scenario: Mode rejected on setup rules
- **WHEN** a file calls `setup("counter", fn, { mode: "single" })`
- **THEN** the call throws an error stating that concurrency modes apply only to triggered rules, and type checking flags the option

#### Scenario: Names shared across both kinds
- **WHEN** a file registers `rule("motion", …)` and `setup("motion", …)`
- **THEN** the second registration throws a duplicate-name error, because both kinds share one namespace of rule names

### Requirement: Rule identity
By default, each rule SHALL have the ID `<path relative to rules dir without extension>#<rule name>`, using `/` as path separator. Rule names SHALL be non-empty strings and unique within a file. A rule MAY instead declare an explicit `id` option, which SHALL replace the default ID, SHALL NOT contain `#`, and SHALL be unique across all loaded files. The ID SHALL be used in logs, storage namespacing, health output and enable/disable configuration.

#### Scenario: Explicit ID survives moving the file
- **WHEN** `lights.ts` registers `rule("motion", …, { id: "kitchen-motion" })` and the file is moved to `rooms/kitchen/lights.ts`
- **THEN** the rule keeps the ID `kitchen-motion` and reads the values it stored before the move

#### Scenario: Explicit ID collision
- **WHEN** two files both declare a rule with `id: "kitchen-motion"`
- **THEN** the file loaded second fails to load with an error naming both files, and the rule from the file loaded first keeps running

#### Scenario: ID of nested rule
- **WHEN** `lights/hallway.ts` registers a rule named `motion`
- **THEN** the rule's ID is `lights/hallway#motion`

#### Scenario: Duplicate name in one file
- **WHEN** a file registers two rules named `motion`
- **THEN** the first registration is kept, the second throws an error naming the duplicate, and the error is logged with the file path

#### Scenario: Conflicting extensions
- **WHEN** both `hallway.ts` and `hallway.js` exist in the same directory
- **THEN** the engine logs an error naming both files and loads neither, because their rule IDs would collide

### Requirement: SDK module with free functions
The SDK SHALL expose rule registration, trigger constructors, listener registration, state helpers and write functions as named free functions importable from one module, so rule files need a single import. The engine SHALL attribute every free-function call to the rule (or, during file evaluation, the file) in whose execution it happens, without the user passing a context.

#### Scenario: Single import
- **WHEN** a rule file contains `import { rule, onChange, isOn, on, forceOff } from "@home-engine/sdk"`
- **THEN** all imported functions are available and the file loads

#### Scenario: Call attributed to the right rule
- **WHEN** rule `lights#porch` calls `forceOn("light.porch")` from inside an awaited callback chain
- **THEN** the engine's logs and dry-run output attribute that service call to `lights#porch`

### Requirement: SDK and typings package
The project SHALL publish the SDK as an npm package so rule authors get editor autocompletion and type checking. Rules SHALL be able to import it at runtime inside the container without installing it themselves.

#### Scenario: Import resolves inside the container
- **WHEN** a rule file imports the SDK package and no user dependency provides it
- **THEN** the import resolves to the engine-bundled version and the rule loads

#### Scenario: Editor support
- **WHEN** a user installs the SDK package in a local copy of their rules directory
- **THEN** their editor offers autocompletion for SDK functions and their parameters

### Requirement: Typed trigger events
Each trigger type SHALL deliver a distinct, typed event object to the rule body. The event's `type` field SHALL discriminate between trigger types, so TypeScript narrows the event shape after checking it.

#### Scenario: Narrowing by event type
- **WHEN** a rule with a state trigger and a cron trigger checks `if (event.type === "state")`
- **THEN** inside that branch the compiler knows `event.entityId`, `event.from` and `event.to`, and outside it does not

### Requirement: Generated Home Assistant typings
The project SHALL provide a command that connects to a Home Assistant instance and generates a TypeScript declaration file. The file SHALL contain the instance's entity IDs, domains and service names (with field names), and the SDK SHALL use it to narrow entity-ID and service parameters.

#### Scenario: Typings generated
- **WHEN** the user runs the typings command with a valid URL and token
- **THEN** a `.d.ts` file is written listing all current entity IDs and services

#### Scenario: Unknown entity flagged in editor
- **WHEN** generated typings are present and a rule references `light.does_not_exist`
- **THEN** the TypeScript compiler reports a type error for that reference

#### Scenario: Works without generated typings
- **WHEN** no generated typings are present
- **THEN** entity IDs and service names are typed as plain strings and rules still type-check

### Requirement: User npm dependencies
If the rules directory contains a `package.json`, the engine SHALL install its dependencies at startup before loading rules. It SHALL use a lockfile when present and skip installation when the lockfile and installed modules are already in sync.

#### Scenario: Third-party package used in a rule
- **WHEN** `package.json` declares `date-fns` and a rule file imports it
- **THEN** the engine installs `date-fns` at startup and the rule file loads successfully

#### Scenario: Installation fails
- **WHEN** dependency installation fails (e.g. no network)
- **THEN** the engine logs the installer output, still attempts to load rule files, and files whose imports cannot be resolved fail individually with a clear error

#### Scenario: No reinstall when unchanged
- **WHEN** the engine restarts and neither `package.json` nor the lockfile changed since the last successful install
- **THEN** no installation is performed
